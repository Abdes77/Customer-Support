## Browser tests after `pnpm verify` (second attempt)

**Symptom.** `TURBO_FORCE=true pnpm verify`, then `pnpm e2e -- --trace off`: the first e2e
run failed and the next ones passed. The orchestrator's failing run had all six admin tests
stuck at sign-in (`page.waitForURL: net::ERR_ABORTED; maybe frame was detached?`, the call
log full of `navigated to "http://127.0.0.1:3100/sign-in"`).

**Reproduced.** Uncached `pnpm verify` (exit 0), then `pnpm e2e -- --trace off`: exit 1,
1 failed, 11 passed. This time the failure was the other face of the same cause: the first
request to `/businesses/new` compiled for more than 20 s (`○ Compiling /businesses/new ...`
in `.next/dev/logs/next-development.log`), so `expect(heading "Onboard a business")` timed
out. A warm run straight after: 12 passed (1.3m), with no "Compiling" line at all. Then
`next typegen` alone (the only thing verify changes in `apps/web`: `.next/types/*` and
`next-env.d.ts`, checked by listing every file under `apps/web/.next` before and after
verify) followed by `pnpm e2e`: the sign-in reload loop, 2 tests failed at 4.0m each before
I stopped it. Running `next typegen` before a short dev-server start once more did not
bring the loop back, so it is a trigger, not a sure one.

**Cause (confirmed).** The tests ran against `next dev`, whose state depends on what ran
before it: Next.js 16.4 keeps a Turbopack cache across dev-server runs
(`turbopackFileSystemCacheForDev` is on by default; `.next/dev/cache`, about 760 MB here)
and compiles each route on its first request.
- The reload loop is the dev server's hot reload, not the sign-in flow. A probe that opened
  `/sign-in` on the looping server and recorded the hot-reload websocket saw, on every page
  load: `{"type":"turbopack-subscribe","path":"static/chunks/apps_web_1anvha4rlo79g._.js"}`
  from the browser, then `{"type":"building"}`, a `turbopack-message` with
  `"type":"restart"` for that chunk and `{"type":"built"}` from the server, then
  `[Fast Refresh] rebuilding` and a new document load (200, no redirect). 23 document loads
  in 3 s; the server logged `✓ Compiled in 2ms` about eight times a second for the whole
  run, even while no admin page was open. Next.js answers a chunk subscription whose first
  update is not just issues with that update (`subscribeToClientHmrEvents` in
  `next/dist/server/dev/hot-reloader-turbopack.js`), and the client reloads the page on
  "restart". A file watcher over the repository saw no file changing during the loop; the
  state is inside that dev-server session (the same cache served fine after a restart).
  The test's fill and click raced these reloads, and the next reload aborted the navigation
  it was waiting for, hence `net::ERR_ABORTED; maybe frame was detached?` (or a timeout).
- Ruled out: a redirect or reload loop in the sign-in flow or in `proxy.ts` (every load was
  a 200 for `/sign-in` started by the hot-reload client; the same flow passes 12/12 on a
  production server below); a stale cookie or secret (every test has a new browser context,
  `LOCAL_AUTH_SECRET` is fixed in `app-server.ts`); port 3100 held by something from
  verify (`lsof` found no listener on 3100 after each verify below); files rewritten by
  verify under `.next/dev` (none; only `.next/types` and `next-env.d.ts` change, and
  rewriting `next-env.d.ts` alone did not trigger anything).

**Fix.** The browser tests no longer use the dev server. `e2e/support/app-server.ts` runs
`next build` (into `apps/web/.next`; the build empties it first except its cache and
`.next/dev`) and then `next start` on the fresh database, with the same environment for both
(`NEXT_PUBLIC_APP_URL` is fixed at build time). A production server has no hot reload and
compiles nothing on request, so neither failure can happen, whatever ran before; it is also
what gets deployed. Auth, in-process jobs and the test channel are chosen by `VERCEL_ENV`,
not `NODE_ENV`, so the app behaves as locally. Playwright now waits until `/sign-in` renders
(proxy, page and database) instead of `/api/health`; its server start timeout is 480 s for
the build (about 30 to 60 s here). No test timeout, retry or skip changed. Docs: DECISIONS
257, the `pnpm e2e` line in CLAUDE.md, ARCHITECTURE "As built (C8)", the comment in
`.github/workflows/e2e.yml`.

Each verify: turbo "21 successful, 21 total" (typecheck), "39 successful, 39 total" (lint),

**CI.** `.github/workflows/e2e.yml` runs `pnpm e2e` on a fresh checkout, which goes through
the same `app-server.ts` (build, then start). The same path locally with no `apps/web/.next`,
no `next-env.d.ts` and no verify before it: `pnpm e2e` → exit 0, `12 passed (1.5m)`.

**Still true for `pnpm dev`.** The dev server's reload loop is a Next.js/Turbopack dev-mode
behaviour, not something in this app. If the local dev server ever reloads a page in a loop,
restarting it (or deleting `apps/web/.next/dev/cache`) clears it.
