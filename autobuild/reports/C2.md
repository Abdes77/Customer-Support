## Found along the way

**1. A `jsonb` string is parsed twice on read (in `packages/db`, not fixed).** postgres.js
parses JSON columns, and Drizzle's `jsonb` column then calls `JSON.parse` on any string it
receives. A stored string that is itself valid JSON changes type:

```
stored strings:   ["55408","true","null","Riley","{\"a\":1}","[1,2]"]
as it is today:   [55408,true,null,"Riley",{"a":1},[1,2]]      # read through Drizzle
with the fix:     ["55408","true","null","Riley","{\"a\":1}","[1,2]"]
```

It surfaced when the demo business's ZIP code setting came back as a number and was rejected
by validation. Objects and arrays are unaffected. What C2 did: every read of a stored setting
value goes through `::text` and one `JSON.parse` (`packages/settings/src/server/rows.ts`),
with a test ("text that looks like JSON stays text"); the hazard and the workaround are in
ARCHITECTURE §8 and DECISIONS 53. What C2 did not do: change `packages/db`, which BUILD_PLAN
puts outside this chunk. The root fix, tried in a scratch script (output above), is to let
Drizzle do the only parse, in `connect()` of `packages/db/src/internal/client.ts`:

```ts
const db = drizzle(client, { schema: tables });
const asText = (value: string) => value;
client.options.parsers[114] = asText;    // json
client.options.parsers[3802] = asText;   // jsonb
```

After it, raw `tx.execute(sql...)` queries return json and jsonb as text (nothing in the
repo reads JSON that way today). Other columns that can hold a bare string:
`lead_fields.value`, `business_playbook_overrides.content`, `audit_log.before` and `after`.

**2. Reading settings as a client user returned defaults silently.** Row-level security
hides the settings tables from client users but not their business, so a read in their
context resolved to registry defaults without any error. The engine now refuses a user
context that is not agency staff, and the service reads for client users in the system scope.

**3. A default that was not valid.** Budget band keys started with a digit, which the slug
format refuses; the registry test that parses every default caught it.

## Decisions worth knowing (all in docs/DECISIONS.md, 40 to 58)

- Keys are flat and each knob is its own setting, so a business overrides one weight and
  inherits the rest. Lists that an agency and a business both add to are two settings
  (`alerts.agency_recipients` and `alerts.recipients`), because overrides replace.
- Invalid stored rows are skipped and reported, never thrown: one bad row must not stop a
  business's bot.
- `client_portal.enabled` is a setting whose value is the column that row-level security
  reads; the store writes the column.
- Careful defaults: prices never disclosed, AI disclosure in the first message (no option to
  deny being an AI), quiet hours 21:00 to 08:00.
- Model defaults: `claude-fable-5-2` everywhere; effort `medium` for replies, follow-ups,
  photo analysis and extraction, `high` for reports and playbooks. C7 should measure replies
  at `medium` against `high`.
- Only knobs for features the spec asks for were declared, not new features.
