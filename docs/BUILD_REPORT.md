# Build report: home-services reply bot

## Read this first: what has and has not been verified

This pull request contains the whole system: a multi-tenant bot that answers customers of US
home-services businesses on WhatsApp, Instagram, Messenger, a website chat and email, qualifies
them, scores them and hands them to the business, with an admin panel for the agency that runs
it. It was built and tested on one computer, with no outside account of any kind.

**Nothing in this system has ever run against a real outside service.** There was no Claude API
key, so every reply the bot wrote in testing came from scripted answers or from a simple
rule-based stand-in, the evaluation suite ran only in its mock mode (which gives no quality
scores), and no playbook was ever generated by the real model. There was no Meta, Google,
Microsoft, Twilio, Calendly or CRM account, no Supabase project (sign-in, file storage and live
updates were exercised only through local stand-ins and a plain PostgreSQL 16 database), no
Inngest Cloud, no Sentry project and no hosted deployment.

What was verified is only what ran on this computer:

1. **`pnpm verify`**: type checking, linting (including the rules on which package may use
   which) and 3,570 automated tests in 140 test files, many of them against a real local
   PostgreSQL database and against fakes of the vendors' APIs built from their documentation.
   It passed uncached (`TURBO_FORCE=true pnpm verify`, exit code 0).
2. **`pnpm eval --mode mock`**: the evaluation suite's 72 simulated conversations run end to end
   against stand-ins. It proves the harness works, not that the bot is good.
3. **The browser tests (`pnpm e2e`)**: a production build of the app on a fresh database, driven
   by a real browser at desktop and phone widths. The bot in these tests is the rule-based
   stand-in, so they prove the plumbing (messages in, replies out on the right channel, lead
   scoring, routing, takeover, the admin screens), not the quality of the replies.

In addition, this last chunk added a load test (`pnpm load:test`) whose numbers describe this
computer only (see "Load test").

Every area below says which of these runs it rests on. Nothing here should be read as "working
in production" or "production-ready": the launch checklist, `docs/HUMAN_TODO.md`, is where each
outside service is tried for the first time, and its Part 5 lists those first tries one by one.

## What was built

The system is a TypeScript monorepo: a Next.js app (`apps/web`) for every screen and HTTP route,
and packages for each part of the logic. `docs/ARCHITECTURE.md` describes the design and has an
"As built" section for each part; `docs/DECISIONS.md` records 300 decisions made along the way.

### Foundations

- **Data, tenancy and sign-in.** One PostgreSQL schema (17 migrations) for agencies, businesses,
  people and roles (agency admin, agency member, client owner, client staff), customers,
  conversations, messages, leads, settings with their history, integrations, alerts and an audit
  log. Row-level security in the database confines every query to what the person or job may
  see; there is no unrestricted database client in the code. Credentials of connected accounts
  are encrypted (AES-256-GCM) before storage and never sent to the browser. Sign-in uses
  Supabase Auth (password and emailed link). _Rests on:_ `pnpm verify` (including a test matrix
  that tries to read and write across businesses as every role on every table), browser tests
  (a client user sees only their business). Not run on a real Supabase project.
- **Settings.** Everything a business might tune is a declared setting with a default, help
  text, allowed scopes (agency, trade, business) and whether a client may edit it: qualification
  criteria and weights, routing, pricing disclosure, persona and AI disclosure, tone and length,
  emergencies, hours and quiet hours, follow-ups, handoff, alerts, scheduling, CRM mapping,
  limits, data retention, model and effort. The settings screen is drawn entirely from these
  declarations; `docs/SETTINGS.md` is generated from them. _Rests on:_ `pnpm verify`, browser
  tests (override and reset at business scope).
- **Message pipeline.** One path for every channel: the webhook checks the provider's signature,
  stores the message once (a repeated delivery is recognized), and hands an event to the job
  runner; one reply job per conversation waits a configurable moment so several quick messages
  get one reply, takes the conversation's turn (one at a time, in order), runs the guards
  (takeover, opt-out, limits), calls the conversation engine and stores the replies; a send job
  per reply keeps them in order, respects each channel's messaging window and retries. _Rests
  on:_ `pnpm verify`, browser tests, load test. The jobs also ran against Inngest's local
  development server early in the build (`autobuild/reports/C3.md`), never against Inngest
  Cloud.

### The bot

- **Conversation engine.** For every turn it assembles the business's profile and knowledge,
  the trade's playbook, the resolved settings, the lead so far and the history, and asks the
  Claude API (the product's default reply model is the setting `claude-fable-5-2`) for a reply
  plus structured actions through tools: update the lead, ask for or analyze a photo, offer
  times or book, escalate an emergency, hand off, mark not a fit, schedule a follow-up, end the
  conversation. A guard checks the reply against the settings (prices, promises, links) before
  it goes out. The system prompt is versioned with tests. _Rests on:_ `pnpm verify` with a
  scripted model (scripted conversations for roofing, HVAC, electrical and remodeling, an
  emergency, a prompt injection, an angry and an off-topic customer behave as specified),
  browser tests with the rule-based stand-in. **Never run against the real model**; how the
  bot actually writes is unknown until HUMAN_TODO steps 24 and 25.
- **Industry playbooks and business knowledge.** A playbook per trade (common jobs, how
  customers describe problems, urgency signals, qualification questions, objections, seasons,
  price norms, permits, vocabulary), generated with the Claude API and its web search the first
  time a trade is onboarded, reused and versioned for later businesses, editable with diff and
  rollback, with per-business overrides. Business facts imported by CSV or an authenticated
  API, optionally read from the business's website through a guarded fetcher, editable in the
  admin panel, and retrieved per turn. _Rests on:_ `pnpm verify` (generation against scripted
  responses for roofing and pest control, reuse by a second roofing business, imports with
  valid and malformed data), browser tests (onboarding with the built-in starter playbook).
  **No playbook has been generated by the real model.**
- **Lead scoring, reports and routing.** After every turn each qualification criterion is
  recorded with its value, confidence and evidence; a score from the weights in settings; a
  written report; and a routing decision (book now, "we'll contact you", always "we'll contact
  you", polite no) that the reply follows. _Rests on:_ `pnpm verify` (15 leads across trades
  under three routing configurations, each result checked), browser tests (a score and a report
  stored for qualified test customers on the website chat, the test channel, WhatsApp, Messenger
  and Instagram).
- **Evaluation harness.** Simulated customers (ready to book, price shopper, tire-kicker,
  renter, out of area, emergency, angry, one-word replies, spam and prompt injection, broken
  English, silent then back) across trades, a judge with a rubric, parallel runs, a baseline
  and an HTML report, run in CI for engine changes. _Rests on:_ `pnpm verify`, mock
  `pnpm eval`. **No quality score exists**: the mock mode evaluates nothing, no baseline is
  saved, and the pass thresholds were set without data.

### Channels

- **Website chat.** A small script per business (one tag) that opens a styled chat bubble,
  collects contact details when settings require, takes photos (made smaller in the browser),
  shows typing and business hours, keeps the session across page loads and receives replies
  live (Supabase Realtime) or by polling; an allowed-origins list and rate limits per visitor,
  address and business. _Rests on:_ `pnpm verify`, browser tests (a qualifying conversation with
  a photo at desktop and phone widths, a reload, a refused origin). Realtime was written from
  memory of its protocol and never met a real project; the tests ran with polling.
- **WhatsApp** (Cloud API): Embedded Signup, signature checks, every inbound type (text, photos,
  voice notes transcribed or answered with "please type", locations, buttons), replies with
  buttons and lists, read receipts and typing, the 24-hour window with approved templates after
  it, template management, delivery statuses, rate limits. _Rests on:_ `pnpm verify` (fixtures
  and a fake Graph API), browser tests (signed webhooks into the production build: a burst of
  messages and a repeated delivery get one reply, a qualified lead, a read status, a forged
  signature refused, a person's reply sent on WhatsApp).
- **Messenger and Instagram:** Facebook Login for Business, messages, attachments, story replies,
  reactions, quick replies, each platform's window rules with the human-agent tag for a
  person's late reply, hand-over when someone answers in Meta's own inbox. _Rests on:_
  `pnpm verify`, browser tests (both platforms through signed webhooks: qualification, the Page
  token used, a person's reply on the same platform).
- **Email:** Gmail (OAuth with push notifications), Microsoft 365 (Graph with change
  notifications) and any IMAP/SMTP inbox (polled every minute); threading, stripping quotes and
  signatures, HTML and plain-text replies with the business's signature, ignoring newsletters,
  auto-replies and bounces, loop protection, sending limits. _Rests on:_ `pnpm verify` (IMAP/SMTP
  against a real mail server inside the tests; Gmail and Graph against fakes), browser tests
  (an IMAP/SMTP inbox connected from the admin panel to a local mail server, then two threaded
  replies). Gmail and Microsoft never ran beyond fakes.

### Handing off

- **Scheduling:** availability from settings and connected Google or Outlook calendars, two or
  three concrete times offered, booking with the lead report in the event, moving and cancelling
  in the conversation, reminders; Calendly as an alternative with single-use links and its
  webhook. _Rests on:_ `pnpm verify` only (fakes of the three APIs).
- **Handoff, alerts, emergencies and follow-ups:** alerts by email, text (Twilio) and WhatsApp
  with a lead summary and a link; an emergency chain that texts the first contact, calls them if
  they do not acknowledge, then moves on; human takeover with manual or idle release;
  follow-ups with per-channel cadence, quiet hours in the customer's time zone, and stopping on
  a reply, an opt-out word or a booking. _Rests on:_ `pnpm verify` (fakes of Twilio and WhatsApp,
  a moved clock), browser tests (takeover and a person's reply on the test channel, WhatsApp,
  Messenger and Instagram).
- **CRMs and webhooks:** HubSpot, GoHighLevel, Jobber, Housecall Pro, ServiceTitan and a signed
  outgoing webhook for Zapier and Make, with field mapping per business, idempotency, retries
  with backoff and errors shown in the admin panel. _Rests on:_ `pnpm verify` (contract tests
  against recorded-style fakes, the webhook against a local receiver). `docs/INTEGRATIONS.md`
  says, per vendor, what was read in its documentation and what was written from memory.

### Admin panel

- **Core:** sign-in, role-aware navigation, business list, an onboarding wizard (profile, trade,
  data import, playbook review, alert contacts, test chat, finish), knowledge editor, playbook
  viewer and editor, settings screen. **Operations:** a live inbox across channels and
  businesses with filters, search, unread state and assignment; the conversation with its lead
  panel, takeover, manual reply, release and internal notes; the lead list with CSV export;
  analytics (conversations, first-response time, qualification rate, meetings booked, where
  conversations stop); connection pages for every channel and integration; a client portal
  limited by per-business permissions; an audit log viewer. _Rests on:_ `pnpm verify`, browser
  tests at desktop and phone widths.

### Security and reliability

A threat model (`docs/THREAT_MODEL.md`) covering prompt injection through every input, tenant
isolation, webhook spoofing and replay, secrets and token refresh, personal data in logs,
server-side request forgery, abuse of the public chat and runaway model spend, each threat with
its mitigation and the test that proves it; then an independent audit of the whole system whose
findings were fixed with tests. Added: rate limits and model-spend caps per customer, business
and agency (emergencies still answered, the customer told to call 911); Sentry error reports
with scrubbing; structured logs with redaction; one trace per customer message; health and
readiness routes; alerts on failed sends and stuck work; data-retention jobs; backup and restore
notes. _Rests on:_ `pnpm verify`, browser tests (security headers, the readiness route). Sentry
never received an event.

### This chunk (launch preparation)

- **Browser journeys on every channel that runs locally**: WhatsApp, Messenger and Instagram
  through correctly signed webhooks and a fake of Meta's Graph API, email through a local mail
  server connected from the admin panel, and the test channel from first message to the lead
  list and its CSV export; the website chat already had its journey. To reach the fakes from a
  production build, three development-only variables were added that a deployment ignores
  (DECISIONS 292).
- **A readiness check for a job runner that never runs** (THREAT_MODEL 4.16): `/api/health/ready`
  now fails when customer messages have waited more than 30 minutes without a reply turn. The
  audit had left this to monitoring; it could be done simply, so it is now a check (DECISIONS
  291), proven by a database test and a readiness test.
- **People management** (added at the end of this chunk, **after** the whole-system security
  audit of C17, and covered by this chunk's own review and tests only): a **People** page for
  the agency's admins and members and a **People** tab per business for its client owner and
  staff. Agency admins add someone by email with a role, change roles and remove access; agency
  members only see the lists; a client owner manages their own staff only if the business turns
  on `client_portal.owner_manages_staff` (off by default). With Supabase, adding sends
  Supabase's invitation (or a sign-in link to an existing account; the screen answers the same
  either way) through its server-side admin API; with the local sign-in the page shows the link.
  Nobody can change their own access, an agency always keeps one admin (a database trigger,
  safe under concurrent changes), and the database refuses direct writes of the membership
  tables by anyone but an agency admin of that agency, never on their own row. Removing access
  takes effect on the person's next request. At most 20 invitations per person a day; every
  change is in the audit log with who made it; no email address is logged (DECISIONS 297 to
  300, THREAT_MODEL 2.12 and 4.17). _Rests on:_ `pnpm verify` (database tests of every role
  writing the membership tables directly, the last-admin rule under concurrency, removal on
  the next request; action tests as every role across agencies and businesses), and a browser
  test at both widths in which an agency admin gives a client owner a login, that person signs
  in and sees only their business, and is turned away after removal. Supabase's invitation
  emails were never sent (HUMAN_TODO step 20 has the live check).
- **The load test** (below).
- **Documents:** the launch checklist (`docs/HUMAN_TODO.md`, rewritten as one ordered list of 41
  steps), `docs/RUNBOOK.md` (deploy, rollback, key rotation, reconnecting channels, daily checks,
  incidents), `docs/ONBOARDING.md` (for agency staff), `docs/META_APP_REVIEW.md` (permissions
  with justifications, screencast script, reviewer instructions) and this report.

## Load test

`pnpm load:test` runs 50 businesses at once, three customers each, every customer sending two
bursts of three quick messages (the second after the reply to the first), through the real
pipeline: webhook, storage, the job runner's debounce (2 seconds) and the business's reply wait
(the default, 4 seconds; both count from a burst's last message, so the reply cannot leave
sooner than 4 seconds after it), the turn lease, the guards with every limit at its default,
the real engine with the rule-based stand-in model, lead scoring, and sending. Then one more
business with its daily reply cap at the lowest allowed value (10).

| Measure | Result |
| --- | --- |
| Customer messages | 918 (900 in bursts, 18 at the capped business) |
| Bursts answered | 300 of 300, each by exactly one reply turn; no failed or superseded turn |
| Order | Every conversation's replies left in the order they were stored |
| Webhook handling | median 0.03 s, 95th percentile 0.69 s, slowest 0.81 s |
| From a burst's last message to the reply leaving | median 5.55 s, 95th percentile 7.21 s, slowest 7.29 s, of which 4.0 s is the configured wait (so 1.55 s, 3.21 s and 3.29 s beyond it; the test fails above 30 s beyond it) |
| Limits at defaults | None tripped |
| Business at its cap | 10 conversations answered, then 4 stopped conversations each got the notice exactly once (with the 911 sentence) and no model turn; a customer reporting a gas smell was still answered |
| Duration | 96 seconds |

**What these numbers are not:** they come from one computer, with local PostgreSQL, the job
runner inside the same process instead of Inngest, and a stand-in model that answers instantly.
A real reply adds the Claude API's time (seconds per turn), Inngest's scheduling and Vercel's
cold starts, and a hosted database is further away. They show that debounce, ordering and the
limits hold under concurrency in this code; they are not a measure of production capacity.

One observation from it: at a business past its daily reply cap, a message about a roof leak was
still answered by the model, because "leak" counts as a possible emergency (flooding), which the
cap deliberately lets through (at most 3 such turns per conversation and 100 per business a day,
THREAT_MODEL 2.8 and 4.1). For a roofer, whose ordinary leads often mention leaks, the daily cap
is therefore softer than it looks, by up to 100 turns a day.

## What remains unverified or open

Each item says where to read more. The launch checklist turns them into steps.

1. **Every outside service is untried.** Claude API (replies, prompt caching, photo analysis,
   web search, playbooks, the evaluation's simulated customers and judge), Supabase (roles and
   row-level security on a real project, Auth, Storage, Realtime), Inngest Cloud, Meta
   (WhatsApp, Messenger, Instagram, Embedded Signup, Facebook Login), Google and Microsoft (mail
   and calendars), Calendly, Twilio, the alert email server, the CRMs, Sentry, Deepgram, and the
   GitHub workflows. `docs/HUMAN_TODO.md` Part 5 has the command for each first try and what a
   pass looks like; its last table lists what is unverified per service.
2. **The bot's quality is unknown.** No real reply has been read, no evaluation score exists and
   no baseline is saved. The evaluation thresholds (pass at 4.0 of 5, floors, allowed drops) were
   set without data and must be revisited after the first live runs (HUMAN_TODO steps 25 and
   40).
3. **Accepted risks** in `docs/THREAT_MODEL.md` section 4, among them: a customer past a limit who
   describes an emergency in words the code does not recognize gets the notice with "call 911"
   instead of a model turn (4.1); spend caps are approximate and can be turned into a day's
   outage by a flood (4.1a, 4.15); anyone can page a business's on-call people by describing an
   emergency, bounded only by the limits and Twilio's spend limit (4.1b); the website chat's
   per-address limit counts per server instance (4.2, 4.3); what is left of email reflection and
   forged bounces (4.4, 4.5); email hand-over by a colleague's mailbox (4.6) and Graph's missing
   message id (4.7); a possible duplicate note in Jobber and Housecall Pro (4.8); no command
   re-encrypts all credentials at once (4.9); browser errors are not reported (4.10); a client
   user talking to Supabase directly reads all of their own business's customer-facing rows
   whatever the portal permissions say, until the Data API is closed and row-level security
   follows those permissions (4.14, HUMAN_TODO step 5).
4. **A dead job runner** (THREAT_MODEL 4.16) is now caught by the `unanswered` readiness check,
   but only after customers have waited half an hour, only when customers write, and only if an
   uptime monitor watches the route. The runbook's daily checks add the live round trip after
   every deployment and once a day (`docs/RUNBOOK.md`, HUMAN_TODO steps 19, 21 and 22).
5. **Three areas the final security audit did not reach** (THREAT_MODEL section 6): a
   line-by-line reading of every server action of the admin panel, the website chat's service
   internals and its browser script, and the CRM connectors' handling of vendor answers. Each had
   its own review when it was built (C15, C16, C8 and C14), and the audit checked that every
   server action goes through the shared cross-site and session checks.
6. **Jobber's connector is partly written from memory**: its developer documentation could not
   be read (a bot challenge). The GraphQL endpoint, headers and most mutations were confirmed
   from Jobber's own published app templates; the token endpoint, refresh-token rotation, the API
   version and whether creating a request needs a form id were not (`docs/INTEGRATIONS.md`,
   HUMAN_TODO step 34).
7. **Choices a person must make before launch** (HUMAN_TODO step 37): the default of
   `follow_up.opt_out_scope` (what the bot does when a customer who opted out writes again); the
   wording of the emergency safety instructions, the AI disclosure and the opt-out texts, with a
   compliance adviser (TCPA, carrier and Meta rules); quiet hours and data retention. **Both
   emergency escalation chains (the business's and the agency's fallback) start empty**: until
   someone is entered, an emergency alerts nobody by phone.
8. **People management is new and less reviewed than the rest.** It was added after the
   independent security audit (THREAT_MODEL section 6) and has been covered by C18's own review
   and tests only (THREAT_MODEL 2.12); it deserves the same independent reading before many
   people are given access. Supabase's invitation and sign-in emails, with the templates of
   HUMAN_TODO step 5, have never been sent (live check: HUMAN_TODO step 20,
   `pnpm --filter @repo/db live:invite`). A client owner's limits on managing their staff are
   enforced by the server, not by row-level security (THREAT_MODEL 4.17). The very first agency
   admin is still made from the command line (`pnpm db:create-admin`). Deleting one customer's
   data on request has no screen yet (`docs/RUNBOOK.md`).
9. **Smaller known limits:** a service radius cannot be checked (no ZIP-code geography; list ZIP
   codes instead, HUMAN_TODO step 38); the Supabase Realtime code for the website chat and the
   inbox was written from memory of the protocol; several vendor details listed under each live
   check in HUMAN_TODO Part 5 (Meta's media hosts, whether Gmail and Exchange keep our message
   headers, Calendly's tracking on single-use links, Twilio's callback signing) can only be
   settled live.
10. **Nothing was deployed.** No production migration, deployment, DNS change or purchase was
    made. The exact commands are in HUMAN_TODO Part 3 and `docs/RUNBOOK.md`.
