# C8 plan: website chat widget

Goal: one script tag per business puts a chat bubble on the business's website. The visitor
talks to the same bot as on every other channel, through `ingest()` and the reply and send
functions of the pipeline. The widget is a public, unauthenticated surface, so everything
below is built around one rule: a request is tied to exactly one business by a public key
that grants nothing else, and the browser never receives a secret or staff-only data.

## Pieces

1. **Protocol** (`packages/core/src/contracts/widget.ts`, new, owner C8). Zod schemas and
   types for every widget API request and response. The server validates with them; the
   browser script imports the types only (no Zod in the bundle).
2. **Server half** (`packages/channels/widget`).
   - `src/adapter.ts`: `createWidgetAdapter({ notifier })`. No webhooks (verify rejects,
     parse throws). `send` accepts text and media: the message is already stored, so
     "sending" means telling the visitor's browser that something changed (a Realtime
     broadcast when configured), then reporting success. `sendTyping` sends the same poke.
   - `src/token.ts`: signed visitor session tokens (HMAC-SHA256 with
     `WIDGET_SESSION_SECRET`, versioned, expiry, constant-time compare). The token carries
     ids only; the `widget_sessions` row is checked on every request (revocation, expiry,
     origin).
   - `src/origins.ts`: origin normalization and matching against
     `channels.widget.allowed_origins` (exact scheme, host and port; an empty list allows
     nothing).
   - `src/limits.ts`: fixed-window counters in `usage_counters` (sessions per IP hash per
     hour, messages per session per minute, messages per business per minute).
   - `src/uploads.ts`: photo checks by magic bytes (JPEG, PNG, WebP, GIF, HEIC), size limit
     from `channels.widget.max_upload_mb`, `channels.widget.photo_upload` switch, stored
     under the tenant's prefix through `@repo/db/storage`.
   - `src/service.ts` (`@repo/channel-widget/server`): `config`, `startSession` (new or
     resumed), `saveProfile` (pre-chat name, phone, email), `postMessage` (text and/or
     photo, builds a `NormalizedInboundMessage` and calls the injected `ingest`),
     `listMessages` (the visitor's own conversation: customer, bot and human messages that
     were sent, signed URLs for their own photos, and a typing flag computed from the
     database), `ensureWidgetConnection`, `rotateWidgetKey`, `widgetEmbedInfo` (the data
     the admin screen of C16 shows: public key, snippet, script URL, allowed origins).
   - `src/realtime.ts`: Supabase Realtime broadcast notifier over the REST endpoint, and the
     per-visitor topic (an HMAC of connection and visitor, unguessable, content-free).
3. **Browser script** (`packages/widget-embed`). Plain TypeScript, no framework, bundled
   by esbuild into one IIFE. Shadow DOM so the host page's CSS cannot break it and ours
   cannot leak. Bubble, teaser, panel (header with logo/title/subtitle, hours notice,
   messages with photos and quick replies, typing dots, pre-chat form, composer with photo
   button, privacy note). Full screen under 640 px, 16 px inputs (no iOS zoom), safe-area
   insets. Session token in `localStorage` per public key; history restored on load.
   Updates: a minimal Supabase Realtime (Phoenix) client when the server hands out a topic,
   otherwise polling that speeds up while a reply is pending and stops while the page is
   hidden. The bundle is generated into `src/bundle.generated.ts` (committed) by
   `pnpm --filter @repo/widget-embed build`; a test rebuilds it and fails when it is stale
   or larger than the budget (gzip).
4. **Routes** (`apps/web/src/app/api/widget/v1`): `widget.js`, `config`, `session`,
   `profile`, `messages` (GET list, POST send with multipart photo). Each one checks the
   Origin against the business's list, answers CORS preflights, never uses cookies, and
   reads bodies with a byte cap. The adapter is registered in `apps/web/src/server/pipeline`.
5. **Settings**: the `channels.widget.*` and `limits.widget_*` settings exist (C2). Add
   `limits.widget_messages_per_business_per_minute`. Business-hours notice from the
   `hours.*` settings via `businessHoursState` of `@repo/ai` (new edge
   `@repo/channel-widget` → `@repo/ai`, downward).
6. **Database**: migration adding `widget_sessions.profile` (pre-chat details, until the
   first message creates the contact) and `last_message_at`; isolation matrix unchanged
   (same table). A storage helper for uploads that have no message id yet:
   `{agency}/{business}/uploads/{session}/{upload}/{file}`.
7. **Playwright** (`apps/web/e2e`, `apps/web/playwright.config.ts`, `pnpm e2e`): the web
   server command prepares a fresh `hsrb_e2e` database (migrate, demo seed, a widget
   connection for Summit Roofing with an allowed origin, pre-chat fields name/phone/email,
   no reply wait, open all week) and starts `next dev`; a tiny static host serves a sample
   page on an allowed and on a refused origin. Specs: a qualifying conversation with a
   photo upload at 1280×800 and 390×844 (offline model), session kept across a reload, and
   a refused origin (no bubble, API answers 403 without CORS headers).

## Tests in `pnpm verify`

Token signing and tampering; origin matching; upload sniffing and limits; adapter
behaviour; service against PostgreSQL (session start and resume, pre-chat enforcement,
message ingest with a photo through a real pipeline, history scoped to the visitor, typing
flag, rate limits, revoked/expired sessions, another business's token refused, origin
removed from the list); the route handlers (CORS, 403 for unknown origins, 413 for big
bodies); the embed bundle's freshness and size.
