# C15 plan: admin core

Goal: the admin panel's core in `apps/web`, on the server functions of C1, C2, C6 and C13.

## Server half

- `packages/db/src/repositories/businesses.ts` (C1's package, the owner of `businesses`):
  `listVisibleBusinesses`, `getVisibleBusiness`, `createBusiness`, `updateBusinessProfile`,
  `setBusinessStatus`, all as the signed-in user (row-level security decides, the role is
  checked first), each write audited. Profile input is a Zod schema (`BusinessProfileInput`).
- `apps/web/src/server/admin`: the session helpers every admin page and action uses
  (`requireStaffBusiness`, `requireVisibleBusiness`, `assertSameOrigin` for every server
  action, on top of Next.js's own Origin/Host check), the settings service
  (`getSettings()`), the view model of the settings screen (sensitive values replaced by a
  summary before anything reaches the browser), masking of alert contacts, and the
  functions behind the server actions (so they can be tested without a request).

## Screens (App Router)

- `/` → `/businesses`. A shell with role-aware navigation: agency staff get Businesses,
  Playbooks, Agency settings and the C16 slots (Inbox, Leads, Analytics, Audit log); client
  users get their business only. Per business: Overview, Onboarding, Knowledge, Playbook,
  Alert contacts, Settings, and the C16 slots Channels and Integrations.
- Business list (search, status, segment, emergency readiness).
- Onboarding wizard `/businesses/new` then `/businesses/[id]/onboarding/[step]`: profile,
  segment (assign: generate or reuse), import (CSV preview, mapping, import; website read),
  playbook review (origin said plainly: generated by Claude, built-in starter without a key,
  written by hand), alert contacts (readiness from `getHandoff().readiness`; not ready is a
  red panel, and finishing needs an explicit acknowledgement), test chat (the dev chat
  component on the test channel), finish (activates the business).
- Knowledge editor: facts by category, add, edit, pin, archive, restore, confirm, delete,
  CSV import, import history. Client users read only.
- Playbooks: segment list; per segment versions, view, diff of two versions, edit as a new
  version (structured section editor), roll back, regenerate. Per business: the effective
  playbook and section overrides.
- Settings: one generic screen for any scope target (agency, segment, business), drawn from
  the registry alone (`findSetting(key).field`), grouped by category and group, showing the
  value in force, where it comes from, the inherited value, override and reset. Sensitive
  settings show "set / not set" and take a new value without showing the old one.

## Tests

- Vitest: db repository tests (roles, isolation), admin helpers (masking, sensitive view
  model, same-origin), the settings screen rendered with `renderToStaticMarkup`, and a
  setting added to the registry through `vi.mock` of a category file appearing on the
  screen with override and reset working at business scope through the real store.
- Playwright (`apps/web/e2e/admin.spec.ts`): onboard a new business end to end through the
  wizard at desktop and phone widths; override and reset a setting at business scope; a
  client user sees only their business.
- Screenshots of every screen at 1280×800 and 390×844 looked at and fixed.
