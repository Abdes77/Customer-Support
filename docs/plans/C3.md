# C3 plan: message pipeline

Goal: every inbound message, from any channel, is verified, stored once and answered by one
debounced, ordered turn per conversation; replies leave through one send path that splits,
orders, retries and dead-letters. A "test" channel and a dev chat page exercise the whole
path with an echo engine until C4 replaces it.

## Design

1. **Jobs (`@repo/jobs`).** Pipeline functions are written once as framework-neutral
   `JobDefinition`s (trigger, debounce, concurrency key, retries, handler, onFailure) against
   a small `StepTools` interface (`run`, `sleep`, `sleepUntil`). Two runners execute them:
   `toInngestFunctions(client, defs)` for Inngest (production, or the Inngest dev server) and
   `createLocalJobRunner()`, an in-process runner with memoized steps, debounce, per-key
   serialisation, retries and onFailure, used by tests and by local development when Inngest
   is not configured. Events are sent through an `EventSender` port with deterministic ids.
2. **Test channel (`@repo/channel-test`).** HMAC-signed JSON webhooks (timestamp + body,
   constant-time compare, five-minute tolerance), parsing into the normalized shapes
   (messages, delivery statuses, human replies, revocation), sending through a pluggable
   transport (in-memory outbox by default, idempotent per key), typing and read signals, and
   a helper that builds signed requests.
3. **Ingest (`@repo/pipeline`).** `handleWebhook(channel, request)` → verify (401), parse and
   re-validate (400), `ingest(parsed)`, 200. `ingest` resolves the tenant through the
   directory, then per message in the business's system scope: duplicate check by
   `(connection, external id)`, contact and identity upsert, open conversation upsert,
   conversation row lock, sequence number, insert, attachments. Emits `message.received`
   with id `msg-received-<messageId>`, then sets `enqueued_at`; an emit failure is a 500 and
   the retry takes the duplicate branch. Delivery statuses move outbound rows forward only;
   `human_agent_replied` stores the person's message and starts a provider-inbox takeover
   when `handoff.provider_inbox_takeover` is on; `connection_revoked` revokes the connection.
4. **Reply turn.** Inngest debounce (static 2 s, key conversation) plus concurrency 1 per
   conversation; inside the run: `plan` (wait until min(message + reply wait, first
   unanswered + longest wait)), sleep, `claim` (exit when a newer message exists and the
   longest wait has not passed; take the turn lease; create a `conversation_turns` row),
   guards (closed, takeover, opted out, blocked, business or connection inactive, longest
   conversation, plus guards registered by C13/C17), attachment download steps, read
   receipt and typing, `generate` (build `EngineTurnInput` from the database and call the
   engine through its ports), `commit` (lease still ours; stale check with at most one
   supersede in a row; outbound rows `queued` with sequence numbers; watermark
   `conversations.handled_through_seq`; release lease), `emit`. onFailure releases the
   lease, marks the turn failed and writes a dead letter.
5. **Send.** Concurrency 1 per conversation; claim the row (`queued` → `sending`, owned by the
   run); wait for earlier outbound messages of the conversation; refuse bot messages during
   a takeover or after an opt-out (`superseded`); messaging-window check; split at
   `maxTextLength` on paragraph, sentence and word boundaries; one memoized step per part
   with idempotency key `<messageId>:<part>`; retryable failures retry (honouring
   retry-after), final failures mark `failed`, emit `message.send_failed`, write a dead
   letter and an in-app alert.
6. **Sweeper.** Every minute per business: re-emit inbound rows left un-enqueued for a
   minute, re-emit outbound rows stuck in `queued`, release expired turn leases.
7. **Registries and stubs.** Adapter registry; action-handler registry with defaults
   (`deferred`, and `rejected` for `offer_times`/`book_meeting`); tool runtime that
   re-validates every action with Zod; echo engine implementing `ConversationEngine`;
   default loaders for playbook and lead snapshot; an empty knowledge retriever; a
   model-call sink writing `model_calls`.
8. **Data.** New table `conversation_turns` (one row per claimed turn: trigger, trace,
   pending range, outcome, actions, versions, usage) and column
   `conversations.handled_through_seq`. Isolation matrix entry.
9. **Web.** `/api/webhooks/[channel]` and `/api/inngest` (thin), the composition root in
   `src/server/pipeline.ts` (adapters, engine, jobs runner chosen from the environment), and
   `/dev/chat` for agency staff: pick a business, chat through the test channel; messages go
   through the same `handleWebhook` as the route.

## Tests

Invariants I1 (bad signature never stored), I2 (duplicate stored and answered once,
sequentially and concurrently), I3 (quick messages get one reply), I4 (turns serialised by
the lease, sends delivered in sequence order even when events arrive reversed), I5 (no
reply and no send during takeover), I7 (retry then success; final failure surfaced). Also:
stale-check supersede, emit failure and recovery, sweeper, statuses, signals, splitting,
window rules, the Inngest functions executed through `@inngest/test`, and the webhook route
round trip in `apps/web`. A separate live check runs the app against the real Inngest dev
server (Docker) and proves the round trip there.
