# C1 plan: data model, tenancy and auth

Goal: a data layer in which crossing a tenant boundary is refused by PostgreSQL itself, for
signed-in users and for background jobs alike, plus sign-in for the admin panel.

## Design

1. **Schema in Drizzle, one file per area** (`packages/db/src/schema`), covering every table
   in ARCHITECTURE §8. Every tenant table carries `agency_id` and `business_id`; a composite
   foreign key to `businesses (id, agency_id)` and composite keys to parents
   (`(conversation_id, business_id)`) make a row that mixes two tenants impossible to store.
2. **Policies next to the tables.** Each table declares its access class with a small builder
   (`tenantPolicies(...)`), which emits the policies for the two restricted roles:
   - `authenticated` (signed-in users): membership-based, through `SECURITY DEFINER` helpers
     in schema `app`. Agency staff see their agency, client users see their own business when
     the business has client logins enabled, and only on the tables marked client-readable.
     Pipeline-written tables (messages, leads, ...) are read-only for users.
   - `app_system` (jobs, webhooks): bound to the tenant that `forBusiness()` / `forAgency()`
     entered, through transaction-local settings. This goes further than "bypass RLS and
     remember the predicate": a job query that forgets `business_id` still cannot leave its
     tenant, so later chunks can use the full query builder safely.
   Secrets live in their own tables with no policy for `authenticated`.
3. **Migrations:** `0000` hand-written foundation (role, helper functions), `0001` generated
   by drizzle-kit from the schema, `0002` hand-written (auth trigger, append-only guards,
   privilege sync). After every migrate, `app.sync_table_privileges()` enables and forces RLS
   on every table and grants each role exactly the commands its policies cover.
4. **Supabase compatibility bootstrap** for plain PostgreSQL (roles, `auth` schema,
   `auth.uid()`, `auth.jwt()`, a minimal `auth.users`), applied automatically when the
   database is not a Supabase one.
5. **Access API** (`createDatabase`): `asUser(user)`, `forBusiness(id)`, `forAgency(id)` each
   run a callback in one transaction under the restricted role; `directory` holds the few
   audited cross-tenant lookups (webhook → tenant, API key → agency). No raw client export.
6. **Credential encryption:** AES-256-GCM, key ring from env with key ids for rotation,
   additional data binds agency, business, purpose and record id.
7. **Tests:** every table with `business_id` is discovered from the catalog and must be in the
   isolation matrix; the matrix is exercised as every role (read, insert, update, delete,
   move to another tenant) and for both system scopes. Test databases are cloned from a
   migrated template, so the suite is fast and parallel-safe, and it starts local PostgreSQL
   or fails loudly.
8. **Auth in `apps/web`:** Supabase Auth (password and magic link) behind a small provider
   interface, session refresh in `proxy.ts`, sign-in page, callback, confirm and sign-out
   routes. A local provider (same interface, users in the compatibility `auth.users`) lets
   the app and later Playwright tests sign in without a Supabase project; it cannot be
   enabled on Vercel.
9. **Seed:** one agency, two businesses (roofing, HVAC), four users (one per role),
   playbooks, knowledge, conversations, leads with scores and reports.
10. **Object storage** (`@repo/db/storage`), added while building because BUILD_PLAN has C8
    building on "Storage from C1": the tenant path convention with a guard, Supabase Storage
    in production, a local folder with signed URLs in development.

## Order of work

schema → migrations → access API → encryption → test helpers → isolation tests → seed →
auth in the web app → storage → scripts, docs, report.
