# C4 plan: conversation engine

Goal: `createEngine()` in `packages/ai` replaces the echo stub. For every turn it builds the
prompt from the business, the playbook, the settings snapshot, the lead, the history and the
channel, calls the Claude API with the model and effort from settings, runs the tool loop
through the `ToolRuntime` port and returns reply drafts plus the executed actions.

Sources checked before building: the Claude API reference bundled with the build tools
(cached 2026-11-03) and the live pages for prompt caching, effort, tool use, strict tool use
and refusals and fallback on platform.claude.com (reachable from the VM on 2026-11-11). There
is no `ANTHROPIC_API_KEY` in the VM, so nothing was sent to the API.

## Design

1. **Model client (`src/model`).** A small port, `ModelClient.call(request)`, with three
   implementations: the Anthropic SDK (`client.beta.messages`, explicit effort, no `thinking`
   or sampling parameters, `tool_choice` auto, server-side fallbacks behind the setting, a
   timeout and an abort signal per call), a scripted client that replays responses and
   records requests (tests of every package), and an offline client that answers by rule
   (local development and end-to-end tests without a key; never on a hosted deployment).
   `callModel()` wraps any client with the `ModelCallRecord` for the sink: inputs, outputs,
   tokens, cache reads, latency. SDK errors become `AppError`s with a deliberate `retryable`.
2. **Prompt (`src/prompt`).** Render order and breakpoints as ARCHITECTURE §5: tools sorted by
   name and the core prompt (identical for every business), the playbook, the business block
   (profile, settings as instructions, core facts; channel-independent), the history as plain
   text turns with a breakpoint on its last block, and last the customer's pending messages
   followed by the turn context (clock, channel rules, hours, lead, routing, retrieved facts)
   as a `role: "system"` message. Customer text only ever sits in `user` content inside
   delimiters. The core prompt lives in a versioned file; a test pins the text of each
   version and a fingerprint of everything rendered from code.
3. **Tools (`src/tools`).** Ten strict tools, one per `EngineAction`. Inputs are validated
   with Zod, then checked against the settings (lead field keys and enumerated values,
   emergency class keys) before the action goes to the `ToolRuntime`; the outcome is the
   tool result. A lead-field catalogue derived from settings is exported for C5.
4. **Turn loop (`src/engine`).** At most `model.max_tool_rounds` rounds, then one call
   without tools. `refusal` → `refused`; `max_tokens` → one retry with more room; retryable
   API errors are thrown so the job retries the step; anything else → `failed`. One overall
   deadline per turn that fits inside the turn lease.
5. **Output guard (`src/guard`).** Deterministic checks on every draft: prompt canary and
   verbatim prompt text, internal markup, length and number of messages, banned phrases,
   links outside the allow-list, prices the settings or the knowledge do not allow, emoji,
   AI disclosure and opening message on the first reply, safety instructions first after an
   emergency escalation. A fixable violation costs one rewrite by the model; what is left is
   repaired in code.
6. **Hours (`src/hours`).** Open or closed now, next opening, federal and custom holidays, in
   the business's time zone; drives the after-hours modes.
7. **Dry run (`src/dry-run`).** `dryRunTurn()` and an in-memory conversation that keeps
   history and lead state, for the evaluation harness (C7) and the scripted tests.
8. **Photo analysis (`src/photos`).** One model call with the images and the question,
   under its own model and effort settings and its own versioned prompt.
9. **Pipeline composition.** `createDomainComposition()` builds the engine with the model
   client from the environment; handlers for `request_photo`, `analyze_photos` and
   `end_conversation`; a guard for conversations the bot ended; a knowledge retriever that
   reads `knowledge_items` until C6. `generate` additionally fills the customer's contact
   details, attachment analyses and the business's contact data (additive contract fields).

## Tests

- Prompt: version pin, render fingerprint, byte-stable cached blocks across turns and clocks,
  breakpoint placement, customer text never outside `user` content.
- Model client: request shape against ARCHITECTURE §5, error mapping, usage with fallbacks.
- Engine: tool loop, parallel tools, invalid inputs, round limit, refusal, `max_tokens`,
  retryable and fatal errors, deadline, after-hours modes, follow-up turns.
- Guard: one test per rule.
- Scripted conversations (mocked model, hand-written in the API's response format): roofing,
  HVAC, electrical and remodeling reach a qualified lead with the expected tool calls;
  emergency, prompt injection, angry customer and off-topic behave as specified.
- Pipeline: a test-channel conversation through webhook, jobs and the real engine; the three
  handlers; invariant I8 (dry run writes nothing).
- Live (needs a key, recorded in HUMAN_TODO): `pnpm --filter @repo/ai live:conversations`
  runs the same customer scripts against the API and checks tool calls and cache reads.
