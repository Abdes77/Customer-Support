# C9 plan: WhatsApp

Goal: a business connects its WhatsApp number through Embedded Signup and its customers talk to
the same bot as on every other channel, through the Cloud API, with the 24-hour
customer-service window enforced and approved templates used outside it.

Meta's docs were reachable through the fetch tool (developers.facebook.com/documentation/...,
read 2026-11-12): webhooks (messages, statuses, template status updates, verification and
signature), send messages (`to` or `recipient` with a BSUID), interactive buttons and lists,
typing indicators, media (URL lookup, download, upload, limits), templates (create, list,
send), Embedded Signup (FB.login, message event, code exchange, subscribed_apps, register),
throughput and the error-code table. Examples use Graph API **v27.0**; that is the default.

## Pieces

1. **`@repo/channel-meta`** (shared with C10): `verifyMetaWebhook` (subscription handshake with
   a constant-time verify-token check; `X-Hub-Signature-256` HMAC-SHA256 over the raw body,
   constant-time), `createGraphClient` (injected `fetch`, version, timeout, JSON and multipart,
   `GraphApiError` with code, details, trace id, HTTP status, usage headers),
   `classifyGraphError` (retryable, retry-after from the code and the
   `x-business-use-case-usage` header, window closed for 131047, auth failures),
   `downloadMedia` (media id → URL → bytes, https and Meta hosts only, size cap),
   `exchangeCode` (Embedded Signup / Facebook Login code → business token).
2. **`@repo/channel-whatsapp`** (adapter, stateless): Zod schema of the webhook; `parseWebhook`
   maps text, image, video, document, sticker, audio (voice flag), location, interactive
   button and list replies, template quick-reply buttons, reactions, contact cards,
   unsupported types; context (reply-to), referral and forwarded flags as metadata; sender =
   BSUID (`from_user_id`) when present, else the phone (`from`); statuses (sent, delivered,
   read, failed with the error); `smb_message_echoes` as `human_agent_replied`; template
   status updates and `account_update` as `provider_event` signals. `send`: text (preview off,
   quick replies as reply buttons when ≤3 titles of ≤20 characters and a body ≤1024, else a
   list of ≤10 rows, else appended as text), media (read from our storage through an injected
   reader, uploaded, sent by media id), templates (named or positional parameters), refusing
   email. `markRead`, `sendTyping` (read receipt plus typing indicator on the newest customer
   message), `fetchAttachment`. Failures mapped through `classifyGraphError`.
3. **`@repo/channel-whatsapp/server`**: Embedded Signup completion (exchange, check that the
   phone number belongs to the WABA, subscribe the app, register the number with a random
   PIN, store the connection and the encrypted `{ accessToken, pin }`), connection info for
   C16 (masked), disconnect, templates (create with named variables from a fixed list,
   sync, delete, status from webhooks), the window fallback resolver (which approved template
   replaces a free-form message once the window has closed, with its variables filled from
   the conversation), the voice-message enricher (transcribe with Deepgram, or a note that
   asks the customer to type, per `channels.whatsapp.voice_messages`), the provider-event
   handler (template status, partner removed → connections revoked, quality rating), the
   `whatsapp-template-sync` cron, and a live check script.
4. **Contracts** (`channel.ts`, additive): `provider_event` signal; `namedVariables` on the
   template message; `WindowFallbackRequest/Result`.
5. **Pipeline** (hooks C3 left, and the three status gaps from the C3 review):
   - send: when the window is closed (or the provider says so on the first part), ask the
     channel's registered window fallback for a template; send it and record what the customer
     saw; without one, fail with `window_closed` (I6). Quick replies are appended as text when
     the channel's button setting is off.
   - delivery statuses: new tables `message_parts` (one row per provider message of an
     outbound message) and `pending_delivery_statuses` (a status for a provider id we do not
     know yet, or for a message still being sent); `finish` records every part and applies the
     held statuses; message status = the furthest status every part reached, failed when any
     part failed before delivery; the sweeper drops held statuses after two days.
   - `provider_event` signals go to registered handlers; attachment enrichers run after an
     attachment is stored; the typing target carries the newest customer message id; webhook
     bodies up to 4 MB (Meta sends up to 3 MB).
6. **Database**: migration 0009 (two tables, an index on `config->>'businessAccountId'`),
   directory lookup `findChannelConnectionsByBusinessAccount`, isolation matrix entries.
7. **Settings**: `channels.whatsapp.staff_reply_template`. **Env**: `META_GRAPH_API_VERSION`
   default `v27.0`, `DEEPGRAM_API_KEY`.
8. **apps/web**: adapter, window fallback, enricher, event handler and cron registered in
   `src/server/pipeline` when `META_APP_SECRET` and `META_WEBHOOK_VERIFY_TOKEN` are set;
   `POST /api/oauth/meta/whatsapp` (Embedded Signup completion, agency staff only);
   `getWhatsApp()` services for C16.

## Tests (`pnpm verify`)

Signature and handshake (good, bad, missing, tampered, wrong token); fixtures for every inbound
type, statuses, echoes, template and account updates; send bodies for text, buttons, list,
media upload, template, read and typing; error classification and rate limits; media download
host checks; Embedded Signup and templates against a fake Graph; window fallback and
enricher against PostgreSQL; pipeline: early status, failed-while-sending, statuses of every
part, template fallback and window rule (I6); apps/web: a signed WhatsApp fixture round-trips
through the webhook, jobs, offline engine and adapter (fake Graph), the 24-hour rule and the
template fallback end to end, and a bad signature never reaches storage (I1).
