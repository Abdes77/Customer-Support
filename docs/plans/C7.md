# C7 · Evaluation harness: plan

Written before building. Owner paths: `packages/evals`, the `pnpm eval` command, the eval CI
workflow, the saved baseline, the HTML report. No `ANTHROPIC_API_KEY` in this VM: everything
is proven against mocked models; the live run goes to `docs/HUMAN_TODO.md`.

## What is evaluated

One flow: a whole customer conversation with the bot, graded as a conversation (not per
turn). The system under test is the real engine as production wires it
(`createDomainComposition()` in `@repo/pipeline`), called in `mode: "dry_run"`.

## Parts

1. **Sandbox** (`src/sandbox`). A throwaway PostgreSQL database (`createTestDatabase()`),
   seeded with one agency, six businesses (roofing, HVAC, plumbing, electrical, remodeling,
   pest control as the "any other segment"), their knowledge and their segment playbooks.
   From it: the production engine, the production knowledge retriever (full-text search) and
   the production playbook loader. Lead state, photos and calendar slots live in the dry
   run's memory (`createDryRunConversation`, `withLeadScoring` with the real rules). Nothing
   is sent; nothing is written to the database after seeding (invariant I8, tested).
2. **Scenarios** (`src/scenarios`). Twelve personas × six segments = 72 scenarios in six
   suites (one per segment), each under a settings profile and a channel assigned by a fixed
   rotation, so every persona meets every profile. Settings = registry defaults → segment
   preset → business values → profile, through the pure resolver. A `--core` subset of 24.
3. **Simulated customer** (`src/simulate`). A Claude call per customer turn (persona, the
   customer's facts, the conversation so far); fixed opening lines and fixed attack lines
   (prompt injection, spam) come from the scenario, not from the model. Silence and return
   are driven by the harness with a `follow_up` turn in between. Without a key: a rule-based
   stand-in behind the same `ModelClient` port.
4. **Grading** (`src/grade`).
   - Code checks on the transcript: the hard rules (length, message and question counts,
     markup, prompt leak, dollar figures, disclosure, opening message, safety instructions
     first, emoji, banned phrases, links) and the behaviour the scenario demands
     (escalation, handoff, spam, expected routing from `assessLead` on the customer's true
     facts, booking only when the rules allow).
   - A judge model (not the model under test) with a strict tool: seven criteria scored 1 to
     5 (qualification, accuracy against knowledge including availability, licenses and
     warranties, setting compliance, engagement, emergency handling, safety, routing) and a
     verdict per rule in force; a reported violation counts only when its quote is found in
     a bot message.
   - Pass: overall ≥ threshold, no criterion under its floor, no failed check, no compliance
     failure.
5. **Runner** (`src/run`). Suites in parallel under one concurrency limit; retries with
   jittered backoff; a wall-clock ceiling per conversation; harness failures go to
   `errors.jsonl`, never into the scores; resume by (scenario, rep); results with full
   transcripts under `evals-output/<run>/`; cost from recorded tokens.
6. **Baseline** (`packages/evals/baseline/live.json`). Saved from a live run only; a mock run
   is never compared with it and can never be saved as it. CI fails on absolute failures and
   on drops beyond the thresholds (overall, per criterion, per scenario).
7. **Report**: one self-contained `report.html` (verdict, persona × segment grid, criteria,
   failures first, every conversation as a chat with what the bot did), plus `summary.md`.
8. **CLI and CI**: `pnpm eval` (live with a key, mock without; `--mode`, `--suite`,
   `--persona`, `--core`, `--reps`, `--save-baseline`, `--resume`). `.github/workflows/eval.yml`
   runs it on changes to `packages/ai` and the other inputs of a reply; without the secret
   it runs in mock mode, which gates only on harness errors and on rules the engine enforces
   in code.

## Tests (in `pnpm verify`)

Scenario matrix shape and the routing oracle; code checks on hand-made transcripts (each
check has a failing case); judge parsing, quote verification and the known-negative cases;
the conversation loop with scripted models (silence and return, handoff, spam, photos,
retries, refusal); the runner end to end against the sandbox with mock models (results,
errors sidecar, resume, I8); baseline save, compare and the live/mock separation; the
report (escaping); the CLI exit codes.

## Order

fixtures and scenarios → sandbox and conversation loop → checks and judge → runner, store,
baseline → report, CLI, CI → docs, `pnpm verify`, report.
