# C2 plan: settings engine

Goal: one place where every tunable behaviour is declared, a resolver every other chunk can
trust, and a store whose writes are validated, versioned and audited. The admin panel (C15)
must be able to draw any setting from its declaration alone.

## Design

1. **Fields** (`src/fields.ts`). A small set of field builders (boolean, text, number,
   select, multi-select, list, object, nullable). Each one returns the Zod schema *and* the
   description a form needs (kind, limits, options with labels, unit, placeholders). A
   setting's type is inferred from its field, so the type, the validation and the control
   cannot drift apart.
2. **Registry** (`src/registry/*`, one file per category). A setting = key, category, label,
   help, field, default, allowed scopes, client-editable flag, sensitive flag. Keys are flat
   (`persona.bot_name`); the exported `AppSettings` type has one property per key. Knobs that
   are tuned separately are separate settings, so a business overrides one weight without
   copying a list. A later chunk adds a setting by adding one entry to a category file.
3. **Resolver, pure part** (`src/resolve.ts`). Merges registry default, then global, then
   segment, then business rows. It never trusts a stored row: a value that fails the schema,
   a row stored at a scope the setting does not allow and an unknown key are skipped, and the
   value falls back to the next layer down. Returns values, the source of each value, a
   stable hash (`version`) and the list of skipped rows. Browser-safe, no I/O.
4. **Server part** (`@repo/settings/server`): reading rows in any database context, the
   `SettingsResolver` from `@repo/core`, a view for the settings screen (effective value,
   inherited value, own override, may-edit), history, and the store.
5. **Store.** All changes of one call are validated first and applied in one transaction:
   scope allowed, value valid, actor allowed (admin for global and segment rows, any staff
   for a business, client users only for client-editable settings and only when the
   business's portal permission allows). Each change bumps the version, appends a row to
   `setting_versions` (with `changed_by` = the signed-in user, as migration 0003 requires)
   and writes an audit entry. Staff write as themselves (RLS decides too); client users have
   no RLS access to these tables, so their checked writes run in the business's system scope.
6. **Docs.** `pnpm settings:docs` renders `docs/SETTINGS.md` from the registry; a test fails
   when the file and the registry differ.
7. **Segment starting values and demo data** (added while building). Presets for roofing,
   HVAC, plumbing, electrical and remodeling as code, written as ordinary segment overrides
   by `applySegmentPreset`; `pnpm db:seed` also loads settings for the demo agency.
8. **Main entry stays browser-safe.** ESLint forbids `node:` and `@repo/db` imports outside
   `src/server`, and a test walks the import graph of `src/index.ts`.

## Catalogue

Categories: qualification, scoring, routing, persona, voice, pricing, photos, guardrails,
conversation, emergency, hours, follow-up, handoff, alerts, scheduling, channels,
integrations, knowledge, client portal, model, limits, data. Rule for what gets declared:
knobs for features the spec asks for, not new features.

## Tests

- registry: every declaration is well-formed, defaults are valid, keys are unique;
- fields: every builder validates and describes itself;
- resolver: precedence, invalid values, scope rules, unknown keys, sources, version hash;
- access: role × scope × client-editable matrix;
- database: rows written behind the engine's back are ignored, versioning, reset, history,
  audit entries, `changed_by`, every role, cross-agency refusal;
- docs match the registry; the main entry has no server imports.

## Order of work

fields → registry types → catalogue → pure resolver and hash → access rules → server (rows,
resolver, store, view) → docs generator → tests → DECISIONS, report.
