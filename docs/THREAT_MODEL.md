# Threat model

Written by C17 (security and reliability) for the independent audit that follows it. For every
threat: what an attacker (or an accident) could do, the mitigation, the file that implements
it and the test that proves it. Accepted risks are listed separately (section 4) with the
reason each is accepted; checks that need a vendor account are in section 5. Paths are
repository-relative; a test is named as `file › test name`.

Read with `docs/ARCHITECTURE.md` §3 (tenancy and security), the "As built" sections, and
`docs/DECISIONS.md` (the numbers below are its entries).

## 1. Assets, actors, trust boundaries

- **Assets.** Customers' messages, photos, contact details and lead reports; businesses'
  settings, knowledge and playbooks; tenant credentials (OAuth tokens, page tokens, IMAP/SMTP
  passwords, CRM keys, webhook signing secrets); platform secrets (env); the model budget;
  the emergency escalation path (a person must hear of a gas leak).
- **Actors.** Customers (untrusted text, photos, emails on every channel); anyone on the
  internet (webhook routes, the widget API, acknowledgement links); vendors' callbacks
  (Meta, Google, Microsoft, Twilio, Calendly); agency staff (trusted within their agency,
  can reach Supabase's REST API with their own token); client users (read-only, one business);
  operators (environment, deployment).
- **Boundaries.** (1) Public HTTP → `apps/web` routes (signature, token or origin checks);
  (2) routes and jobs → PostgreSQL (row-level security, one tenant per transaction);
  (3) customer text → the model (data blocks, narrow validated tools, output guard);
  (4) our process → vendors and user-supplied hosts (pinned, checked addresses);
  (5) our process → logs and Sentry (redaction and scrubbing).

## 4. Accepted risks

| # | Risk | Why it is accepted | What limits it |
| --- | --- | --- | --- |
| 4.1 | An emergency described in words none of the business's emergency phrases contain, written by a customer past a rate limit or cap, gets the code-written notice ("If anyone is in danger right now, call 911.") instead of a model turn. | Recognizing an emergency by meaning needs a model call, which is exactly what a cap stops; making every capped message a model call would make the cap meaningless under a flood. | The notice itself tells them to call 911; the limits are generous by default (60 messages an hour, 100 replies a day, $5 per customer per day); the team is alerted; `limits.on_limit` = handoff puts a person on the conversation; the phrase lists are the business's to extend. |
| 4.2 | The per-address limit in front of the widget's `config` and `session` counts per server instance. | No Redis in the stack (DECISIONS 11); a database counter before the database is a contradiction. | Per-address sessions per hour are also counted in PostgreSQL; a platform rate-limit rule on `/api/widget/v1` is in HUMAN_TODO 19. |
| 4.3 | Polls of many sessions from many addresses are cheap reads that are not limited deployment-wide. | Each poll is one indexed read; sessions per address are limited. | HUMAN_TODO 19 (firewall rule). |
| 4.4 | Reflection when the forged sender's domain has no DMARC policy (`dmarc=none`), or the receiving IMAP server adds no Authentication-Results: the bot answers a forged address once with its own text (no quote of the attacker's). | Without DMARC there is no way to tell a forged From from a real one; refusing all such mail would refuse real customers. | No quote on a first email; the reply is about the business's services; per-thread, per-contact (2× thread) and per-inbox daily limits. |
| 4.5 | A recipient of one of our emails (who knows its Message-ID and its recipient) can forge a bounce that marks it failed. | The receiving providers' own DSN paths could not be checked without live samples (HUMAN_TODO 14). | It changes one status and raises a "send failed" alert to the team; nothing is sent to anyone. |
| 4.6 | A colleague answering a customer from another mailbox (with the shared inbox in copy) does not hand the conversation over; the bot may keep answering. | INBOX "From" is unauthenticated (DECISIONS 193) and a DMARC-verified path could not be checked against live Gmail/Exchange headers. | Staff take over from the admin panel; connecting the colleague's mailbox makes its Sent folder a hand-over source; `channels.email.skip_staffed_threads`. |
| 4.7 | Microsoft Graph's `sendMail` returns no id; our copy in Sent is recognized by headers or by words (DECISIONS 194). | Graph's API, not ours; the draft-then-send path needs a live check first. | Own-send recognition by Message-ID, loop header and words; HUMAN_TODO 14 live check. |
| 4.8 | Jobber and Housecall Pro may get a second note after a lost answer; their records themselves are recovered (DECISIONS 244). | A duplicate note is cosmetic and visible; the vendors' note listing APIs were not confirmed from their docs. | The record is not duplicated; HUMAN_TODO 17. |
| 4.9 | There is no command that re-encrypts every stored credential under a new key at once. | Rotation works without it (old keys decrypt, writes re-encrypt); C18 owns the runbook. | HUMAN_TODO 4. |
| 4.10 | Browser-side errors are not reported to Sentry (`NEXT_PUBLIC_SENTRY_DSN` is declared, unused). | The admin panel renders customer text in the browser; a browser error message could carry it, and the server-side scrubber does not run there. Server errors (including those of server components) are reported with Next.js's digest. | `onRequestError` covers server rendering, routes and actions. |
| 4.11 | Deleting a conversation by retention deletes its model calls (token counts and costs) with it. | Cascades keep tenant data consistent; spend caps only look at the current day and month, far inside the minimum retention of 30 days. | `data.conversation_retention_days` ≥ 30. |
| 4.12 | Inbound conversations never "close", so conversation retention counts from the last message. | No flow closes conversations; the help text's "after it was closed" reads as "after it went quiet". | DECISIONS (C17). |
